Website Audit Report
Date: April 7, 2026
Project: Future Pathways — Career Assessment Platform
Stack: Express.js + React + TypeScript + PostgreSQL (Neon) + Stripe + Passport.js
Auditor: Comprehensive Static Analysis

Executive Summary
Future Pathways is a full-stack career guidance and assessment platform built on Replit. The codebase demonstrates a commendable security posture for a Replit-Agent-generated project: CSRF protection via double-submit cookies, bcrypt password hashing, AES-256-GCM encryption for stored API keys, server-side Stripe price calculation, Drizzle ORM preventing SQL injection, and a thorough Helmet.js security header configuration. These are non-trivial implementations that speak well of the codebase's security intent.

However, several production-breaking issues require immediate attention before any deployment. The most critical is server/db.ts:13, which logs the full DATABASE_URL — including credentials — to stdout on every server boot. A second production-breaker is the OAuth callback URL fallback, which constructs a *.repl.co URL when BASE_URL is unset; if OAuth providers are configured but BASE_URL is not, every Google/Microsoft login will redirect to a dead Replit URL. There is also a isComplete vs isCompleted field name mismatch in the admin bulk PDF route that will silently skip every completed assessment. Finally, the VITE_STRIPE_PUBLIC_KEY client-side env var is undocumented and unvalidated, meaning the entire payment flow will silently fail in production if the key is not injected at build time.

The production-readiness risk level is MEDIUM-HIGH. The core security architecture is sound, but the Replit-origin artifacts, missing environment documentation, file system assumptions, and several scattered bugs make this codebase not yet safe to deploy to a public-facing production environment without remediation.

🔴 Critical Issues — Production Breakers
CRIT-1: DATABASE_URL Logged to Console on Every Boot
File: server/db.ts:13

console.log("DATABASE_URL:", process.env.DATABASE_URL);

Impact: The full PostgreSQL connection string (including username, password, host, and database name) is printed in plaintext to stdout. In any hosted environment — Replit deployments, Railway, Fly.io, Heroku — stdout is captured in platform logs that may be accessible to multiple team members, support staff, or third-party log aggregators. This is a credential leak.
Fix: Replace with console.log("Database connection: configured"); or remove the line entirely.

CRIT-2: OAuth Callback URL Falls Back to Dead Replit Domain
File: server/auth.ts:103

const baseUrl = process.env.BASE_URL ||
  `https://${process.env.REPL_SLUG}.${process.env.REPL_OWNER}.repl.co`;

Impact: If BASE_URL is not explicitly set in the production environment, and REPL_SLUG/REPL_OWNER are also absent (true on any non-Replit host), the constructed URL becomes https://undefined.undefined.repl.co. All Google and Microsoft OAuth callbacks will redirect to that invalid URL. OAuth will be completely broken.
Fix: Add BASE_URL, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, MICROSOFT_CLIENT_ID, MICROSOFT_CLIENT_SECRET to ENV_VARS.REQUIRED (if OAuth is enabled) or at minimum to ENV_VARS.OPTIONAL with a startup warning. Add a check:

if (!process.env.BASE_URL) {
  console.error("WARNING: BASE_URL is not set. OAuth callbacks will be misconfigured.");
}

File: server/services/email.ts:32

Impact: If APP_URL is not set, all password reset emails will contain links pointing to https://futurepathways.replit.app. Users who receive reset emails will be redirected to the wrong domain, making password reset completely broken on any non-Replit deployment. HIGH-2: In-Memory Rate Limiting — Ineffective in Multi-Instance Deployments
File: server/middleware/rateLimiter.middleware.ts, server/auth.ts:13
Impact: express-rate-limit defaults to an in-memory store. In a multi-process or autoscale environment (which .replit's deploymentTarget = "autoscale" implies), each instance has independent counters. An attacker can bypass rate limits by distributing requests across instances. Login brute force protection (5 attempts per 15 min), payment abuse protection, and all other rate limits are effectively circumventable.
Fix: Use a Redis-backed store (rate-limit-redis) or database-backed store for distributed rate limiting.

Executive Summary
Future Pathways is a well-structured full-stack application with a commendable baseline of security practices: AES-256-GCM encryption for sensitive API credentials, double-submit CSRF protection, comprehensive Helmet.js security headers, bcrypt password hashing with zxcvbn strength analysis, parameterized ORM queries, Stripe webhook signature verification, and rate limiting on all sensitive endpoints. The developer has clearly invested effort in security, and many common vulnerabilities are absent or well-mitigated.

However, the application was built and tested exclusively within the Replit environment, and several deployment-critical issues exist that will cause failures or expose sensitive data in any production environment. The single most dangerous active issue is console.log("DATABASE_URL:", process.env.DATABASE_URL) in server/db.ts:13, which broadcasts the full database connection string — including credentials — to stdout on every server startup. Equally critical is a field name bug (isComplete vs isCompleted) in the admin bulk PDF route that causes the feature to silently return zero results. There is also a hardcoded http://localhost:5000 in the admin bulk PDF route that breaks in any production or custom-port deployment.

Beyond those, the application has meaningful Replit dependency leakage (OAuth fallback URLs, email fallback domain, SSRF allowlist), ephemeral filesystem usage for file uploads, a missing frontend environment variable declaration for the Stripe publishable key, a Replit-specific Vite plugin that is not gated out of production builds, and a superadmin authorization logic inconsistency that creates a split security model. These issues are fully correctable and none require architectural changes. Overall, the codebase is approximately 70% production-ready, and reaching full readiness requires addressing the 8–10 issues listed in the Critical and High sections below.

File: server/db.ts:13

File: server/routes/admin.routes.ts:1110

const baseUrl = process.env.NODE_ENV === 'production'
