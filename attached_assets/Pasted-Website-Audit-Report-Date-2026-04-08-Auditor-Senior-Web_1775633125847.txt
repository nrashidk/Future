Executive Summary
Future Pathways is a moderately mature career-guidance SaaS built on a Node.js/Express + React/Vite stack with PostgreSQL via Neon's serverless driver. The codebase shows deliberate security awareness — bcrypt password hashing, Zod input validation, DOMPurify sanitisation, Stripe webhook signature verification, CSRF double-submit cookies, and Helmet security headers are all present. The PostgreSQL session store is correctly used; no SQLite or in-memory database was found.

However, several issues will cause production breakage or create real security risk. The most serious production-breaker is that the /uploads/ directory (which stores organisation logos and admin-uploaded files) is never mounted as a static route, meaning all uploaded logos will return 404 in production. A second critical finding is that VITE_STRIPE_PUBLIC_KEY is not declared anywhere in the repository — the Stripe payment UI will be broken for all users unless this variable is injected at build time. Additionally, the OAuth callback URL construction in server/auth.ts falls back to a Replit-specific URL pattern (REPL_SLUG.REPL_OWNER.repl.co) when BASE_URL is unset — OAuth logins will silently break if BASE_URL is not provided in the production environment.

Code quality concerns include: the getSuperadminEmails() helper function is copy-pasted identically across eight different server files with no shared import; ESLint is entirely absent (no config file, so no linting has ever run); TypeScript compilation reports three errors including missing @types/node and @types/vite declarations; and Puppeteer's --no-sandbox flag is used in both PDF generation endpoints, which is appropriate for containerized deployments but is explicitly commented as a Replit requirement, suggesting it was not evaluated for the final production environment.

🔴 Critical Issues — Production Breakers
CRIT-1 — Uploaded files (/uploads/) are never served as static assets
File: server/vite.ts:79, server/routes/admin.routes.ts:371, server/routes/files.routes.ts:10
Description: The production static file server (serveStatic in server/vite.ts:79) only mounts dist/public. The uploads/ directory is never passed to express.static(). Organisation logo URLs are stored as /uploads/<filename> (admin.routes.ts:371), but those paths will return 404 in production because nothing serves them.
Recommended fix: In server/vite.ts (or server/index.ts), add before the catch-all:

app.use('/uploads', express.static(path.join(process.cwd(), 'uploads')));

Additionally, implement a proper S3/object-storage strategy for production so files survive deployments (see CRIT-3 below).

CRIT-2 — VITE_STRIPE_PUBLIC_KEY is undefined at build time
File: client/src/pages/Checkout.tsx:19–21
Description: The Stripe publishable key is loaded via import.meta.env.VITE_STRIPE_PUBLIC_KEY. This value is baked into the client bundle at vite build time. No .env, .env.production, or documented VITE_STRIPE_PUBLIC_KEY declaration exists in the repository. The constant STRIPE_PUBLISHABLE_KEY is listed in server/config/constants.ts:64 as an optional server-side env var but is never forwarded to the Vite build context. Without VITE_STRIPE_PUBLIC_KEY set at build time, loadStripe() is called with undefined, Stripe silently fails, and the payment page is broken for all users.
Recommended fix: Set VITE_STRIPE_PUBLIC_KEY=pk_live_... in the build environment (Replit Secrets → exposed to build, or a .env.production file added to the deployment pipeline). Note: this key is publishable (safe to embed in client bundles), not the secret key.

CRIT-3 — File uploads use local ephemeral disk storage
File: server/routes/files.routes.ts:10–11, server/routes/admin.routes.ts:16
Description: All uploaded files (logos, data exports, credential ZIP files) are written to process.cwd()/uploads on the local filesystem. On ephemeral/autoscaling infrastructure (the .replit deployment target is autoscale), this directory is wiped on every deployment or container restart. Every uploaded logo and file will be permanently lost after a deploy.
Recommended fix: Integrate cloud object storage (AWS S3, Cloudflare R2, or similar). Use multer-s3 or upload to S3 directly in the route handler, then store the public URL in the database instead of a local path.

CRIT-4 — OAuth callback URL falls back to Replit-specific domain
File: server/auth.ts:104

const baseUrl = process.env.BASE_URL || `https://${process.env.REPL_SLUG}.${process.env.REPL_OWNER}.repl.co`;

Description: If BASE_URL is not set in production, the OAuth callback URL is constructed from REPL_SLUG and REPL_OWNER (Replit-specific injected variables). Outside Replit, both variables are undefined, producing https://undefined.undefined.repl.co as the callback URL. Google/Microsoft OAuth will reject this redirect URI, breaking all social login.
Recommended fix: Add BASE_URL to the ENV_VARS.REQUIRED list in server/config/constants.ts, or at minimum add it to ENV_VARS.OPTIONAL with a startup warning. Remove the Replit fallback URL; there is no safe default for a production OAuth callback.

CRIT-5 — Superadmin email exposed in committed .replit config file
File: .replit:48

[
userenv.shared
]
SUPERADMIN_EMAILS = "nrashidk@gmail.com"

Description: A real personal email address is hardcoded in the .replit configuration file, which appears to be committed to the repository. This both exposes PII and leaks the exact email that grants superadmin access to the application. Anyone who reads the repository can target this email for account takeover attempts to gain platform-wide admin privileges.
Recommended fix: Remove the [userenv.shared] block from .replit entirely. Set SUPERADMIN_EMAILS via Replit Secrets (encrypted, not in source). Add .replit to .gitignore if it contains environment-specific values, or redact this section.

🟠 High Priority Issues
HIGH-1 — TypeScript compilation fails: missing @types/node and @types/vite
File: tsconfig.json:17 ("types": ["node", "vite/client"])
Description: Running npx tsc --noEmit produces three errors. The @types/node package exists in devDependencies (version 20.16.11) but the TypeScript resolver cannot find it — likely a workspace or moduleResolution: "bundler" conflict. This means TypeScript type checking is silent on all node built-in types, potentially masking type-level errors across the entire server codebase.
Recommended fix: Ensure @types/node is correctly installed and visible (npm ls @types/node). Consider separating tsconfig.json into server and client variants (which have different lib and types needs). Fix the baseUrl deprecation warning by adding "ignoreDeprecations": "6.0" to compilerOptions.

HIGH-2 — No ESLint configuration — zero linting enforced
File: (repository root — no eslint.config.js exists)
Description: npx eslint exits immediately with "ESLint couldn't find an eslint.config file." The project has no .eslintrc.* and no eslint.config.js. This means no linting rules (no-unused-vars, no-console, security plugins, etc.) have ever run. The devDependency list also does not include eslint or any ESLint plugins.
Recommended fix: Install ESLint and create a flat config (eslint.config.js) with rules appropriate for a React + Node TypeScript project. Recommended plugins: @typescript-eslint, eslint-plugin-react, eslint-plugin-security.

HIGH-3 — Console logging of credentials to browser in production
File: client/src/pages/Checkout.tsx:137

console.log("Your Login Credentials - Please Save:", data.credentials);

Description: After a successful group purchase, the new user's plaintext username and password are logged to the browser console. Anyone with DevTools access (the user themselves, or an attacker with physical access, XSS, or a browser extension) can read these credentials. The comment "Also log to console as backup" indicates this is intentional, but it violates the principle of not storing or transmitting credentials in plaintext.
Recommended fix: Remove the console.log entirely. The credentials modal (CredentialsModal) is the correct channel. If "backup" is needed, prompt the user to copy credentials from the modal; do not write them to an observable log.

HIGH-4 — console.log debug statements left in server route handlers
File: server/routes/assessment.routes.ts:85, 95, 113, 131
Description: Server-side console.log statements log Kolb/RIASEC score objects, assessment IDs, and user IDs to stdout in production. With morgan('combined') already logging HTTP requests, these duplicate logs increase noise and may expose internal data structures in production logging systems.
Recommended fix: Replace with logger.debug(...) calls (which are gated behind !isProduction in server/utils/logger.ts), or remove entirely. The logger utility is already implemented — it just is not being used consistently.

HIGH-5 — Puppeteer --no-sandbox flag with no production justification
File: server/routes/recommendations.routes.ts:277–284, server/routes/admin.routes.ts:1056–1061
Description: Both PDF generation endpoints launch Chromium with --no-sandbox and --disable-setuid-sandbox. The code comment explicitly states: "Note: --no-sandbox is required in containerized environments like Replit." This flag bypasses the OS process sandbox, which is a meaningful security reduction. While necessary in some container environments, it should be confirmed that the production hosting environment also requires it, and if not, it should be removed.
Recommended fix: Test PDF generation in the actual production environment without --no-sandbox. If the production host supports user namespaces (most modern Linux containers do), remove the flag. If required, document why in a security decision record.

HIGH-6 — Rate limiting is IP-based with no distributed backend
File: server/middleware/rateLimiter.middleware.ts:8–50, server/auth.ts:13–18
Description: All rate limiters use express-rate-limit with the default in-memory store. In an autoscale deployment (multiple processes/pods), each process maintains its own counter. A user can send 5× the configured limit by spreading requests across N instances. This entirely defeats rate limiting on auth endpoints (login, registration, password reset).
Recommended fix: Use rate-limit-redis or rate-limit-postgresql as the store so counters are shared across all instances. Since the project already has PostgreSQL, a PostgreSQL-backed store is straightforward.

HIGH-7 — CSRF_TOKEN comparison is not timing-safe
File: server/middleware/csrf.middleware.ts:81

if (cookieToken !== headerToken) {

Description: Token comparison uses JavaScript's !== operator, which is a short-circuit string comparison. Theoretically, a timing side-channel attack could distinguish matches from mismatches. For a 64-character hex token this risk is low but real.
Recommended fix: Use crypto.timingSafeEqual(Buffer.from(cookieToken), Buffer.from(headerToken)) for the CSRF token comparison.

MED-4 — BASE_URL, GOOGLE_CLIENT_ID, MICROSOFT_CLIENT_ID, and EMAIL_FROM are not validated at startup
File: server/config/constants.ts:55–69, server/utils/env-validation.ts
Description: The startup validator only checks DATABASE_URL, SESSION_SECRET, SUPERADMIN_EMAILS, and DB_ENCRYPTION_KEY as required. BASE_URL (needed for OAuth callbacks), GOOGLE_CLIENT_ID/GOOGLE_CLIENT_SECRET/MICROSOFT_CLIENT_ID/MICROSOFT_CLIENT_SECRET (OAuth providers), EMAIL_FROM (email from address), and VITE_STRIPE_PUBLIC_KEY (Stripe client) are not listed at all. MED-5 — dangerouslySetInnerHTML used in chart component
File: client/src/components/ui/chart.tsx:81–98
Description: The chart component uses dangerouslySetInnerHTML to inject CSS custom properties. The injected content (--color-${key}: ${color}) is derived from a colorConfig array that originates from component props. If any consumer passes untrusted color values from an API response, this is an XSS vector.
Description of actual risk: In current usage the color values come from a static THEMES constant in the same file, so the risk is low. However, itemConfig.color can come from props.
Recommended fix: Sanitize the color value with a CSS color validation regex before injection, or use inline style attributes on DOM elements instead of injecting a <style> tag.

MED-6 — Assessment draft data stored in localStorage includes sensitive context
File: client/src/components/RiasecStep.tsx:116, 134, client/src/components/CVQStep.tsx:102, client/src/pages/Assessment.tsx:320
Description: RIASEC response data, CVQ values response data, and the full pending assessment object (name, age, grade, gender, subjects, interests, personality traits, etc.) are stored in localStorage. localStorage is accessible to any JavaScript running in the same origin, including injected scripts from a successful XSS attack. Additionally, browser extensions can read localStorage.
Note: This is not authentication token storage (which would be OWASP A07), but it is PII of minors (ages 13–18) being stored in a weakly protected client-side store.
Recommended fix: For draft persistence, use sessionStorage instead of localStorage (cleared when the tab closes). For assessment submission recovery, consider server-side draft storage (the assessment can be created with isCompleted: false).

MED-7 — No Content Security Policy nonce — unsafe-inline used for styles
File: server/index.ts:29–32

styleSrc: ["'self'", "'unsafe-inline'", "https://fonts.googleapis.com"],

Description: 'unsafe-inline' for style-src allows any inline style attribute or <style> tag to execute. While CSS injection is lower severity than JS injection, it enables CSS exfiltration attacks (extracting data via CSS selectors and request URLs) and clickjacking via CSS overlay.
Recommended fix: Move Tailwind/component inline styles to external CSS classes during the build. If inline styles are unavoidable, use nonce-based CSP for styles. At minimum, document why 'unsafe-inline' is necessary.

MED-8 — memorystore package is installed but never used

Description: The memorystore npm package is in dependencies (not devDependencies) but no code imports or uses it. Sessions are correctly stored in PostgreSQL via connect-pg-simple. This is dead weight that marginally increases bundle size and attack surface.

MED-9 — Organisation logo uploads accept image/svg+xml without sanitisation
File: server/routes/admin.routes.ts:363

const allowedTypes = ['image/png','image/jpeg','image/gif','image/webp','image/svg+xml'];

Description: SVG files are XML documents that can contain embedded <script> tags, javascript: href links, and external entity references (XXE). If an organisation admin uploads a malicious SVG and it is served from the same origin, it becomes a stored XSS vector.
Recommended fix: Either remove SVG from the allowed list, or pass uploaded SVGs through an SVG sanitizer (e.g., svgo or DOMPurify with SVG support) before saving.

Executive Summary
